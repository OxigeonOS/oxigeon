# OLC — Building In-Game

```
> olc thornhollow
You are now building in 'thornhollow'.

> dig north sunken_yard
You dig north into thornhollow.sunken_yard.
  Written: game/areas/thornhollow/sunken_yard.lua
  Written: game/areas/thornhollow/_meta.lua

> north
Sunken Yard
A new room.
Obvious exits: south

> olc off
You are no longer building.
```

Online Creation is the builder's half of the world: rooms made from inside the
game, written to **real Lua files** on disk, and loaded on the next boot exactly
as a hand-written area is.

That last part is the design. The alternative — rooms in a database, edited
in-game and never seen by a text editor — makes the world uneditable by every
tool that already exists, unreviewable in a pull request, and unrecoverable from
a backup that is not a database dump. `codegen_d` writes Lua because Lua is what
the loader reads.

## The three parts

| | |
|---|---|
| **`olc_d`** | who is building, and in which area. Session state, in memory: if the server restarts you are not building any more, which is correct. |
| **`codegen_d`** | turns a room's data into a Lua source file, and reads one back. |
| **`dig`** | the verb that makes a room and links it, in one step. |

## `olc <area>` / `olc off`

Enters building mode for an area. Everything that follows — `dig` in particular
— is scoped to it, so `dig north yard` cannot accidentally write into somebody
else's area because you forgot where you were.

Building mode is **cleaned up on disconnect**, as one of `on_disconnect`'s
protected steps. A session that dropped mid-build leaves no lock and no state.

> [!NOTE]
> `olc` and `dig` both require the `olc` permission. Grant it through a role —
> `role allow builder cmd.olc` — rather than by making everyone an admin. See
> [Permissions](./permissions.md).

## `dig <direction> <room_id>`

```
dig north sunken_yard
dig n sunken_yard              -- abbreviations expand
dig north thornhollow.yard     -- a fully-qualified id also works
```

One command, four effects:

1. An exit from the room you are standing in, in that direction.
2. The target room, if it does not exist yet.
3. The **return exit**, in the opposite direction. A one-way exit is almost
   always a mistake at dig time, and making it the default would mean every
   builder discovers it by walking into a room they cannot leave.
4. Both rooms written to disk.

The reverse direction comes from the same table `movement.lua` uses, so `dig`
and walking cannot disagree about what the opposite of `northeast` is.

## What gets written

`codegen_d.write_room_file` produces a plain data table — the same shape an
area file has always had:

```lua
-- game/areas/thornhollow/sunken_yard.lua
-- Generated by codegen_d. Safe to edit by hand.
return {
    id          = "thornhollow.sunken_yard",
    short       = "Sunken Yard",
    description = "A new room.",
    light       = 2,
    exits = {
        south = "thornhollow.square",
    },
    items   = {},
    actions = {},
}
```

**Safe to edit by hand**, and that is not a courtesy — it is the round trip. A
builder digs the shape of an area in-game, then opens the files and writes the
prose, and the next `dig` reads what is there rather than overwriting it.
`codegen_d.read_room_data` and `update_room_exits` exist for exactly that: a
later dig adds an exit to a file whose description somebody has since rewritten.

`_meta.lua` is written alongside, so the area has a name, a title and a status
without anyone remembering to create one.

## The round trip

The property worth testing, and the one that says OLC works:

```
build in-game  ->  files on disk  ->  reload  ->  walk it
```

```
> olc sandbox
> dig north entrance
> dig east side_room
> verify areas/sandbox/entrance.lua      -- compiles without executing
> reload areas.sandbox.entrance
> north
```

`verify` is worth the habit. It compiles a file and does not run it, so a
syntax error in a generated area is caught before a reload takes the area down.

## Permissions and the jail

Everything OLC writes goes through `write_file`, which is:

- **jailed** to the mudlib and game roots — a room id cannot contain a path
  that escapes them, and
- **checked** against `[directories]` in `permissions.toml`, where `/areas` is
  gated on `dir.write.areas`.

That rule used to be commented out, which made the builder role a label rather
than a boundary. It is live, and `tests/staff.rs` boots with the repository's
own `permissions.toml` to prove it — a test against the default config would
pass whether the rule were there or not.

## What it will not do

- **No room editor.** `dig` makes a room and links it; the description, the
  scenery, the actions and the lfuns are written in a file. An in-game editor
  for prose would be a worse text editor than the one you already have, and it
  would have to reimplement multi-line input, undo and colour.
- **No live-editing of a room somebody is standing in.** A file is written and a
  `reload` picks it up. That is one step rather than zero, and it is the step
  where `verify` fits.
- **No deletion.** `delete_file` exists and OLC does not call it. Removing a
  room that other rooms link to is a decision with consequences a builder should
  make deliberately, in a file, in a diff.
- **No conflict handling.** Two builders in one area will overwrite each other's
  files. The answer is the same as for two people editing one file anywhere
  else, and pretending otherwise would need a locking model nobody has asked
  for.
